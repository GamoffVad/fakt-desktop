# Нагрузочный тест и отказы конвейера FAKT — 25.09.2026

Сводка фактически выполненных прогонов. Подробности каждого прогона (окружение, команда, временной ряд памяти,
проверки) — в файлах `load-test-2026-09-25-<прогон>.md/.json` рядом.

**Ограничения достоверности.**

- LLM заменён локальным детерминированным имитатором `Fakt.Testing.LocalLlmSimulator`. Он нагружает конвейер
  (разбор промпта, ответ со всеми полями, evidence из текста записи, проверка ExtractionValidator), но **не является
  провайдером и не доказывает работу реальных API**. Скорость конвейера с реальной моделью определяется моделью.
- Всё измерено на Windows 11 Pro 25H2 (Intel Core Ultra 9 285K, 24 логических процессора, 95 ГБ ОЗУ),
  SQL Server 2025 Developer на той же машине. **Windows 7 SP1 x64 недоступна — на целевой ОС ничего не проверялось.**
- Остальное — настоящие классы приложения: ProcessingService/JobSession/FilePipeline, BatchExtractor,
  ResilientLlmClient, ExtractionValidator, PythonWorkerClient + Python worker (Python 3.8.10, pandas 2.0.3,
  numpy 1.23.5; open_reader/read_chunk), SqlStorage/SqlFactWriter, DatabaseAdmin (миграции V001–V008),
  SqlSearchRepository. Временная база `FaktLoad_<guid>` создаётся прогоном и удаляется после него.
- Память: `GetProcessMemoryInfo` процесса .NET и процесса Python worker (private bytes, рабочий набор; пики ведёт ОС),
  плюс опрос каждые 250 мс для временного ряда.

## Как воспроизвести

```
dotnet build Fakt.sln -c Release
set FAKT_PYTHON=D:\Projects_new\Fakt\worker\build\out\python\python.exe
tools\Fakt.LoadTest\bin\Release\net48\Fakt.LoadTest.exe --records 1000000 --label 1m-csv
tools\Fakt.LoadTest\bin\Release\net48\Fakt.LoadTest.exe --records 50000 --label 50k-csv

tools\Fakt.LoadTest\bin\Release\net48\Fakt.LoadTest.exe --records 1000000 --format fixed --skip-search --label 1m-fixed
tools\Fakt.LoadTest\bin\Release\net48\Fakt.LoadTest.exe --records 1000000 --format jsonl --skip-search --label 1m-jsonl
tools\Fakt.LoadTest\bin\Release\net48\Fakt.LoadTest.exe --records 200000 --fault-429 0.02 --fault-503 0.002 --fault-timeout 0.002 --fault-invalid-json 0.01 --fault-missing-id 0.01 --fault-duplicate-id 0.005 --fault-unknown-id 0.005 --skip-parse-only --skip-search --label 200k-csv-llm-faults
tools\Fakt.LoadTest\bin\Release\net48\Fakt.LoadTest.exe --records 20000 --latency-ms 200 --concurrency 4 --skip-parse-only --skip-search --label 20k-csv-slow-llm

dotnet test tests\Fakt.IntegrationTests\Fakt.IntegrationTests.csproj -c Release --filter "FullyQualifiedName~PipelineFaultTests"
```

Параметры конвейера — значения приложения по умолчанию (chunk 5000, пакет LLM 10 записей, 2 параллельных запроса,
очередь 8, SQL-пакет ≤ 500), кроме явно указанных. Предел бюджета задания снят (по умолчанию 5000 запросов —
задание на миллион записей встало бы на паузу). Файл создаётся генератором
`tools/testdata/generate_testdata.py --large N --large-format csv|fixed|jsonl` в `testdata/large` (в Git не хранится).

## Выводы

1. **Память не растёт с размером файла.** 50 тыс. и 1 млн записей: пик .NET 105 и 109 МБ private, Python worker
   60 и 62 МБ; управляемая куча после полной сборки мусора в обоих случаях 2,4 МБ. На 10/25/50/75/90 % файла
   .NET держится в пределах 67–105 МБ, Python — 53–54 МБ, без тренда. Читатель опережает фиксацию не больше чем
   на один chunk Pandas (≈ 5 000 записей) плюс окно очереди; при медленной модели чтение ждёт (не более 5 080 из
   20 000 записей в пути).
2. **Узкое место без модели — SQL-фиксация.** Цикл фиксации однопоточный и занят 92–93 % времени. В транзакции в
   среднем 59 строк (максимум 110–120), хотя SQL-пакет 500: окно конвейера = очередь + параллельность + 2 = 12 пакетов
   LLM × 10 записей, больше готовых строк не бывает. С очередью 64 — 314 строк на фиксацию и +30 % (3 139 зап/с) при
   той же памяти; стоимость строки в SQL всё равно доминирует (≈ 0,40 мс на строку при 59 строках, ≈ 0,31 мс при 314).
   Это вопрос проектирования (связь окна и SQL-пакета) — поведение не менялось.
3. **С реальной моделью скорость определяет модель.** При ответе 200 мс и 4 параллельных запросах — 191 зап/с
   (96 % теоретического предела 200). Оценка, не измерение: при 1–2 с на пакет из 10 записей и 2 параллельных
   запросах миллион записей займёт 14–28 ч.
4. **Отказы LLM под нагрузкой не теряют и не дублируют записи** (200 тыс. записей, 21 209 запросов, 1 101 ошибка:
   429 — 453, 503 — 40, тайм-аут — 32, битый JSON — 212, пропущенный ID — 181, повтор ID — 79, чужой ID — 104).
   Скорость падает до 734 зап/с: повтор 503/тайм-аута без Retry-After ждёт до 2 с (полный jitter) и всё это время
   занимает один из двух слотов параллельности.
5. **Чтение не узкое место:** worker занят 6 % времени конвейера. Без LLM и SQL: CSV 33–36 тыс., фиксированная
   ширина 36 тыс., JSON Lines 29 тыс. записей/с (Python 3.8 + pandas, движок python).
6. **Полнотекстовый индекс** отстаёт от записи: после окончания конвейера в очереди 50–60 тыс. документов,
   индекс догоняет за 30–40 с.

## Отказы конвейера (`PipelineFaultTests`, категории SqlServer и PythonWorker)

Файл из 2 000 синтетических записей (chunk 250), настоящие ProcessingService/JobSession, Python worker и SQL Server
(временная база FaktIT_…), имитатор LLM. После каждого сценария результат сравнивается с прогоном без отказов:
реестр строк 1..N без пропусков и повторов, наблюдения без повторов ключа, те же счётчики и тот же SHA-256
содержимого (реестр, ошибки, основные поля, [ALL] без job_id и времени, индекс идентификаторов, поисковая проекция).
Два прогона подряд: 12/12 (≈ 54 с), затем весь проект интеграционных тестов 19/19.

| Сценарий | Что проверяется | Итог |
|---|---|---|
| Процесс worker завершён между двумя read_chunk | ошибка видна (задание «Ошибка», сообщение о сбое worker), граница непрерывна, продолжение после «перезапуска приложения» пропускает подтверждённые записи | пройден (до исправления клиента — «Читатель не найден») |
| Процесс worker завершён во время read_chunk | то же | пройден |
| KILL сеанса SQL внутри транзакции фиксации (Shared Memory и TCP) | повтор через 2 с, транзакция откатилась, повтор — обычная фиксация | пройден |
| Разрыв простаивающего соединения писателя между фиксациями (Shared Memory и TCP) | транспортная ошибка распознаётся как временная, переподключение, временные таблицы создаются заново | пройден |
| База недоступна дольше всех повторов (READ_ONLY) | конвейер останавливается, записанное не теряется, продолжение после восстановления | пройден (см. замечание 3 ниже) |
| Потеря подтверждения после COMMIT, повтор в том же процессе | повтор той же фиксации распознан по CommitId (Duplicate), данные не изменены | пройден |

## Найденные и исправленные дефекты

1. **Сбой worker маскировался сообщением «Читатель не найден»** (`PythonWorkerClient`). Если процесс worker падал
   между запросами, следующий read_chunk молча запускал новый процесс, где читателя нет, и задание завершалось
   ошибкой «Ошибка чтения файла: Читатель не найден». Теперь читатель привязан к процессу, который его открыл: после
   гибели процесса сообщается «Процесс worker завершился (код …): открытое чтение файла прервано». Покрыто тестом
   `WorkerProcessKilledMidFile…(between_requests)` (без исправления падает с исходным сообщением).
2. **Python worker держал ~740 МБ лишней памяти на 24 логических ядрах** (`fakt_worker_main.py`). numpy при импорте
   поднимает OpenBLAS с потоком на ядро и ~32 МБ закреплённой памяти на поток: 777 МБ private bytes и 27 потоков у
   простаивающего worker против 38 МБ и 4 потоков с `OPENBLAS_NUM_THREADS=1`; worker не выполняет матричных
   вычислений. Рабочий набор не менялся (54 МБ), но закреплённая память засчитывается в предел commit-памяти системы.
   В конвейере пик Python снизился с ~800 до 60 МБ private.
3. **Память и время одного read_chunk росли с позицией в файле** (`fakt_worker/parsers`). Движок python pandas 2.0.3
   на каждый chunk вычисляет `set(skiprows) - set(range(pos))` — множество всех прочитанных номеров строк. На
   300 тыс. записей пик chunk рос с 6,4 до 16,2 МБ, время — со 140 до 285 мс; в прогоне на 1 млн пик Python 118–120 МБ
   к 600–700 тыс. записей. Пустое множество заменяется на `None` с функцией пропуска «ничего» (тот же смысл). После
   исправления пик 61–62 МБ на всём файле, чтение CSV 30,5 → 33–36 тыс. зап/с. Покрыто тестом worker
   `test_chunk_memory_does_not_grow_with_position_in_file` (без исправления: пик последних chunk 3,2 МБ против 0,7 МБ).

## Замечания без изменения кода (вопросы проектирования и риски)

1. **SQL-пакет фактически ограничен окном конвейера** (см. вывод 2): при настройках по умолчанию 59 строк на
   транзакцию вместо 500.
2. **Прогресс в памяти занижается после повтора-дубликата.** Если подтверждение фиксации потеряно, повтор с тем же
   CommitId возвращает нулевые счётчики, и событие прогресса показывает, например, 1 980 извлечённых записей из
   2 000 (в базе — 2 000, границы и счётчики `FaktFileProgress` верны). Журнал фиксаций не хранит счётчики исходной
   фиксации.
3. **При длительной недоступности базы `JobSession.RunAsync` завершается исключением.** Конвейер корректно
   останавливается (записанное сохранено, граница непрерывна), но затем JobSession записывает статусы в ту же
   недоступную базу (`UpdateJobFileAsync`, `UpdateJobAsync`) и выбрасывает `SqlException` вместо статуса «На паузе»:
   в памяти сеанса статус «Ошибка» с текстом ошибки базы, событие `StateChanged` не приходит, в базе задание остаётся
   «Выполняется», файл — «Обработка». Продолжение после восстановления базы работает (проверено тестом).
4. **Бюджет задания сбрасывается при продолжении после перезапуска:** `ResumeJobAsync` создаёт `BudgetTracker` с нуля.
5. **Отмена по таймеру паузы в `FilePipeline`** может теоретически вызвать `Cancel()` уже освобождённого
   `CancellationTokenSource`, если пауза нажата в последние 200 мс перед завершением файла (найдено чтением кода,
   не воспроизводилось).

## Что не проверено

- Windows 7 SP1 x64 (недоступна): ни совместимость, ни память и скорость на целевой ОС.
- Реальные провайдеры LLM: только имитатор.
- Удалённый SQL Server по сети: сервер локальный (TCP проверен только через localhost в тестах отказов).
- Интерфейс WPF при этих сбоях: проверен прикладной слой (ProcessingService/JobSession), не окна.
- Машины с меньшим числом ядер и объёмом памяти: цифры памяти получены на 24 логических процессорах и 95 ГБ ОЗУ.
