| Проект | Назначение |

| `src/Fakt.Application` | Сценарии: задание обработки с паузой/продолжением и бюджетом, конвейер файла, определение структуры, пакетное извлечение с делением пакетов, оценка запуска, настройки и права. |

| `tests/`, `tools/` | Модульные, интеграционные (SQL Server, отказы, реальный LLM) и нагрузочный тесты. |

## Обработка файла

1. **Сканирование** папки (рекурсивно, без чтения содержимого): имя, путь, размер, время изменения; бинарные и неподдерживаемые файлы отмечаются сразу.
2. **Определение структуры**: worker читает образец (первые 5 строк, с определением кодировки) → модель возвращает контракт структуры (JSON Schema) → приложение проверяет контракт, уточняет границы колонок фиксированной ширины по образцу, для файлов без заголовка сверяет подобранные моделью имена колонок с форматом значений → worker проверяет структуру парсером на ограниченном фрагменте и возвращает предпросмотр. Недостаточный образец → «Требует настройки» и кнопка «Расширенный образец».
3. **Регистрация источника**: потоковый SHA-256 содержимого, `FileCode` = `T_` + 18 цифр (уникальный), отпечаток файла (размер, время) для контроля изменений.
4. **Конвейер** (все очереди ограничены, память не растёт с размером файла):

```
worker: чтение chunk (5 000 записей) ─► пакеты по токенам и числу записей ─► очередь (32) ─► N запросов к LLM
      ▲ окно: очередь + параллельность + 2 пакета                                              │
      └──────────── чтение ждёт, если окно занято ◄── фиксация в SQL по порядку ◄── проверка ответа
```

   - Проверка ответа: результат для каждой записи (схема ограничивает число строк ответа, пропущенные записи запрашиваются повторно, пакет делится при обрезке), значения должны встречаться в тексте записи, даты проверяются по календарю и формату, типы фактов — по формату значения; лица и факты, которых нет в записи, отбрасываются с причиной.
   - Фиксация — атомарно по завершённым пакетам в порядке файла: `SqlBulkCopy` во временные таблицы и одна транзакция; реестр строк, уникальный индекс наблюдений и `CommitId` делают повторную фиксацию безопасной (идемпотентность при сбое после COMMIT).
   - Контрольная точка — последний подряд зафиксированный номер записи; продолжение после паузы, сбоя worker или базы начинается с неё без дублей.
5. **Пауза** — мягкая остановка с сохранением выполняющейся работы; **Стоп** — отмена. Изменённый после паузы файл не продолжается (новая версия источника).

## Хранение

Основные таблицы (имена настраиваются сопоставлением):

- `SourceFiles(ID, FileCode, FileName, …технические поля)` — источник;
- `PersonFacts(ID, Фамилия, Имя, Отчество, Дата рождения, Место рождения, ALL, ID_FileName → SourceFiles.ID)` — наблюдение о лице; `ALL` — JSON (`ISJSON`) со всеми фактами, происхождением полей (колонка и фрагмент), неразрешёнными полями, отклонёнными кандидатами и сведениями о модели.

Служебные таблицы (схема настраивается): `FaktJobs`, `FaktJobFiles`, `FaktFileProgress`, `FaktRowOutcomes`, `FaktRowErrors`, `FaktCommitLog`, `FaktSearchDocs`, `FaktFactValues`, `FaktSchemaMigrations`.

Миграции `database/migrations/V001–V008` применяются явно (с просмотром SQL) и не удаляют таблицы и данные. Исключение — новая пустая база, созданная приложением автоматически: к ней сразу применяются все миграции.

| Миграция | Назначение |
|---|---|
| V001 | Основные таблицы SourceFiles и PersonFacts |
| V002 | Технические поля SourceFiles |
| V003 | Технические поля PersonFacts для идемпотентной записи |
| V004 | Проверка ISJSON и значение по умолчанию для ALL |
| V005 | Служебные таблицы заданий, checkpoint и ошибок |
| V006 | Поисковая проекция и индекс идентификаторов |
| V007 | Полнотекстовый каталог и индекс (русский, LCID 1049) |
| V008 | Индексы фильтров поиска |

## Поиск

- Полнотекстовая проекция `FaktSearchDocs` (ФИО, даты, место рождения, факты из ALL, имя и код файла) с индексом Full-Text Search; запрос — `CONTAINSTABLE` по словам (все слова / любое / фраза / префикс), пользовательский ввод экранируется.
- Типизированные фильтры: ФИО (точно или по началу), диапазон дат рождения, место, тип факта, идентификатор (телефон, счёт, документ — по нормализованному ключу в `FaktFactValues`, телефон в любом формате записи), имя и код файла, ID наблюдения и файла.
- Серверная пагинация (страница + 1 строка), отдельный подсчёт общего числа, отмена и защита от устаревших результатов.
- Карточка наблюдения: все поля, все факты из ALL с происхождением, файл и код файла.

## Безопасность

- Роли «Администратор» и «Оператор» назначаются учётным записям и группам Windows по SID; владелец задаётся при первом запуске; права проверяются в сервисах при каждом действии.
- Секреты — DPAPI (пользователь или компьютер с ACL); ключ API привязан к схеме, хосту и порту провайдера, пароль SQL — к серверу и имени входа.
- Журнал JSON Lines маскирует ключи, пароли, телефоны, счета и адреса почты; тексты записей и сырые ответы модели — только в подробном режиме, включаемом на ограниченный срок.
- Файлы — данные, не инструкции: промпт запрещает выполнение указаний из данных, ответы проверяются по схеме и тексту записи; worker запускается без секретов и без сети.

## Сеть и совместимость

TLS 1.2 задаётся явно для HTTP-клиента; SQL-подключение использует SChannel ОС (на Windows 7 нужен ключ реестра TLS 1.2 Client). Подробно — `docs/COMPATIBILITY.md`.
